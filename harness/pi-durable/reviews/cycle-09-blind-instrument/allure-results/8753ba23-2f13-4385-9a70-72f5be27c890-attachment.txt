<!doctype html><html lang="en"><head><meta charset="utf-8"><meta name="viewport" content="width=device-width,initial-scale=1"><title>Löyly API guide</title><link rel="stylesheet" href="/style.css"></head><body><header><a class="brand" href="/">♨ löyly</a><a href="/">Back to sauna bookings</a></header><main class="doc"><div class="eyebrow">Public product interface</div><h1>Booking record API</h1><p>JSON over HTTP. All paths below begin with <code>/api/houses/HOUSE_ID/</code>, except house creation. POST bodies use <code>Content-Type: application/json</code>. Refused domain requests return <code>status: "refused"</code>, a reason and the policy version. Invalid input returns HTTP 400. Requests are applied atomically to a persistent record before the server responds.</p><div class="banner">This is a local cooperative workbench. The house and acting household/role are explicit working context, not authenticated credentials. Manager-mediated bookings are recorded at the manager's desk, not automatically sent to an outside manager. Do not expose this administrative build to an untrusted network.</div><h2>Quick example</h2><pre class="json-output">POST /api/houses/demo/bookings
{"household":"12","role":"tenant","resource":"8","weekday":"Tuesday","start":"17:00"}

GET /api/houses/demo/views
GET /api/houses/demo/views?date=2030-01-08
GET /api/houses/demo/bookings/BOOKING_ID/history

POST /api/houses/demo/releases
{"household":"12","bookingId":"BOOKING_ID","date":"2030-01-08","mode":"FREE"}

POST /api/houses/demo/releases/OFFER_ID/take
{"household":"3","role":"tenant"}</pre><p>Use a future Tuesday for an occurrence. The current house clock is available from <code>GET config</code>. Calendar times are named local calendar values interpreted on the workbench's UTC clock. There is no floating-hour or bare timestamp slot identity: a dated slot is always <code>{date, resource, start}</code>; a recurring one uses <code>{weekday, resource, start}</code>.</p><h2>Endpoints</h2><div class="table-wrap"><table><thead><tr><th>Method / path</th><th>Purpose / body</th></tr></thead><tbody>

{
  "id": "house-a", "name": "House A", "now": "2030-01-01T10:00:00Z",
  "resources": [{
    "id": "8", "name": "Dressing room 8", "sauna": "F", "group": "A",
    "duration": 90,
    "days": ["Tuesday"], "starts": ["17:00", "18:30"]
  }],
  "policy": {
    "authority": "board", "route": "self-service", "bookerRoles": ["tenant"],
    "operatorRole": "manager", "billingRole": "billing", "disputeRole": "manager",
    "chooseDays": 14, "noticeDays": 30,
    "standingPriceRef": "house standing tariff",
    "salePriceRef": "house resale tariff", "classCaps": {"family": 1}
  }
}</pre><p>For time-class calendars, replace <code>days</code> and <code>starts</code> with <code>"windows": [{"weekday":"Tuesday","start":"17:00","timeClass":"family"}]</code>. Group names determine queue eligibility and scarcity scope. They never cross house boundaries. Booker roles are explicit per request. A class cap counts active/upcoming confirmed dated bookings (and recurring rights) of that class only.</p><h2>Limits</h2><p>No equipment commands, numeric resale prices, sale-proceeds distribution, payment collection, invoice delivery, no-show penalties or third-hand subtenant policy are invented. Existing-booking migrations across policy revisions are outside this cut. The sample ph 8 calendar includes the documented Tuesday; other sample windows are explicit illustrative configuration, not an assertion about the cooperative's full calendar.</p><p>A notice without a selected holding retains the queue-head choice right after the choose deadline; no undocumented default choice is made. Use <code>choose</code> before the selected holding can lapse.</p></main></body></html>
