# Löyly implementation

Zero-dependency Node.js HTTP application. Run `./test.sh`, then `./start.sh 8901` from any directory. Node 18 or later is required. No package download or build is needed. The browser at `/` exposes bookings, release/take/withdraw, queue and notice actions, date-specific derived views, configurable houses, authorized policy revision and dispute history. `/api/docs` lists the public JSON routes; `/api/state` exposes the complete record for inspection.

`DATA_FILE` can select an independent JSON record file; the default is `impl/data.json`. Successful requests persist atomically within the synchronous Node request decision, so concurrent requests are serialized at the domain decision. Dates and instants are UTC. A clock can be advanced through the management screen or `POST /api/clock {now: ISO_INSTANT}` for lifecycle checks. `POST /api/reset {now: ISO_INSTANT}` restores the documented Soukanvuori calendar and clears all records; use a separate DATA_FILE for isolated testing.

A booking accepts `{house, household, role, resource, day, start}`; adding `date` makes it a one-occurrence booking. Default house is `soukanvuori`, default booker role is `shareholder`. Requests are recorded including refusals and policy versions. The manager-mediated route is made explicit in the UI and has no resident queue. The shared domain decision serves both mediated and self-service routes.

House creation accepts `{id,name,route,bookerRoles,bookingOperator,operationsRole,billingRole,disputeRole,authorityRole,caps,chooseDays,noticeDays,resources}`. A resource accepts `{id,name,days,starts,group,timeClass,duration}`. Defaults are 90-minute windows, 14-day choice and 30-day lapse. Only explicit `days` and `starts` are offered. Policy revision accepts `{actor,authority,version,effectiveAt,...ruleChanges}`; actor must equal that house's authorityRole. This is a demonstration of configured operating roles, not an authentication service.

Release creation accepts `{bookingId,household,date,mode: "FREE"|"SALE"}`; take/withdraw accepts `{household}`. Queue entry accepts `{house,group,household,role}`. Scarcity evaluation accepts `{house,group}`. Notice choose accepts `{household,bookingId}`; confirm and decline accept `{household}`. The holder remains current until lapse, regardless of pending claims. With no selected holding at lapse the notice remains unresolved rather than inventing an automatic choice policy.

Views are recalculated from bookings and occurrence transfers, never maintained as independent copies. Billing amounts and collection, equipment control, future occurrence migration after forfeiture and unspecified automatic selection remain outside scope.

`acceptance.test.js` drives all 47 stamped scenarios through HTTP, including 100 standing-booking races and a released-occurrence race. The closed-day usability test verifies a replayable suggested request; the genuinely independent blind-reader judgment belongs to the external gate and cannot be claimed by this builder. Tests were written before the server implementation; initial red output is retained in `red.log`. The initial failure was a module-scope boot failure, followed by a passing full public-surface suite after a local package boundary and implementation were added.
